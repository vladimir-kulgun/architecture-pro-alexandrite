# 1. Проблемы, влияющие на заказы и работу клиентов
## 1.1. Узкое место: MES рассчитывает стоимость слишком долго (2–30 минут)

- Один инстанс.
- Синхронная блокирующая логика.
- Нет масштабирования.
- API теперь зовут внешние партнёры → лавинообразный рост нагрузки.

**Последствия:**
Зависание очереди, задержки статусов, потерянные заказы, холостые циклы ожидания.

## 1.2. CRM получает заказы только через сообщения из RabbitMQ от MES

Любые задержки внутри MES → задержка создания заказа в CRM.

**Проблема:**
Неспособность обработать всплеск входящих запросов.

## 1.3. Заказы теряются или приходят с большой задержкой

Симптомы: «клиенты не получили заказы», «ждали месяцами».

Возможные причины:
- Сообщения RabbitMQ не подтверждены / не потреблены.
- Отсутствие Dead Letter Queue.
- Нет Retry/Backoff.
- CRM/MES не обрабатывают повторные сообщения (идемпотентность отсутствует).
- Монолитный потребитель RabbitMQ.

## 1.4. У MES нет реального SLA ответа для API

Внешние партнёры жалуются, что:
- не получают результат,
- не знают, приняли ли заказ,
- нет понятной модели асинхронности.

# 2. Проблемы в UI/UX внутренних пользователей (операторов MES)
## 2.1. Страница списка заказов в MES грузится слишком долго

Обычно это означает:
- Неправильные SQL-запросы (SELECT * FROM Orders без индексов).
- Нет лимитов, сортировки, батчей.
- Один инстанс БД для чтения.
- Хранение большого массива данных в одной таблице.
- Дашборд пытается построить агрегаты в реальном времени.

**Следствие:** операторы не могут выбрать новый заказ → простаивает производство.

## 2.2. Операторы видят только ИСТОРИЮ заказов вместо актуальных

Симптом: «хотели фильтр по статусам — не помогло».

Значит:
- проблема не в UI,
- проблема в медленной БД или API,
- или в том, что MES пересчитывает стоимость статусов каждый раз.

# 3. Проблемы интеграции и обмена сообщениями
## 3.1. RabbitMQ — единственная точка отказа

Один брокер → при росте нагрузки получает:
- переполненные очереди,
- высокий latency,
- потерю сообщений,
- невозможность горизонтального масштабирования.

## 3.2. Отсутствие трекинга жизненного цикла заказа (SAGA / Process Manager)

Вся логика разнесена по 3 приложениям: магазин → MES → CRM.

Нет центра, который:
- принимает конечные решения,
- восстанавливает после ошибок,
- гарантирует корректный порядок статусов,
- ведёт retry orchestration.

**Следствие**:
- рассинхронизация статусов,
- зависание на промежуточных стадиях,
- невозможность понять, где на самом деле застрял заказ.

# 4. Проблемы данных и БД
## 4.1. Каждая система имеет свою базу

Нормально, но:
- нет согласованного Event Store,
- нет audit-log по статусам,
- нет общего источника правды (Single Source of Truth),
- нет CDC/репликации на аналитические нагрузки.

## 4.2. База MES перегружена

По косвенным признакам:
- медленные SELECT на списки заказов (не хватает индексов),
- вычисления стоимости могут идти из БД → блокировки,
- нет отдельного read replica.

# 4.3. CRM также скрытый источник узких мест

Если CRM зависает при записи заказа (например, если очередь «давит»), MES тоже зависает.

# 5. Архитектурные проблемы
## 5.1. Каждый сервис — одиночный инстанс

Ограничения:
- нет горизонтального масштабирования,
- один баг → падение,
- при росте заказов производительность падает нелинейно.

## 5.2. CI/CD «ручной» и тормозит выпуск версий

- dev → auto, но release/prod → вручную,
- QA делает только ручное тестирование,
- релизы задерживаются месяцами.

**Следствие**: технический долг падает сверху как бетонная плита.

## 5.3. Нет нагрузки (performance) тестов

Симптомы явно показывают, что рост нагрузки не был протестирован заранее.

# 6. Организационные проблемы
## 6.1. Команда маленькая для 3 приложений и RabbitMQ

- 2 backend Java, 1 backend C# — мало для такой нагрузки,
- 1 QA вручную — bottleneck,
- DevOps один на всё.

## 6.2. Релизы блокируются high-багами → команда боится релизиться

Это типичный признак проблем архитектуры — страх трогать код.

# 7. Потенциальные технологические риски
## 7.1. API для внешних клиентов не масштабируется

Нет throttling, rate limits, очередей для медленных операций.

## 7.2. Долгие операции вызывают таймауты у клиентов

Системы-партнёры могут отправлять повторные запросы → дублей заказов становится больше.

## 7.3. Нет мониторинга:

Не указано:
- нет Prometheus,
- нет Grafana,
- нет алертов,
- нет трейсинга (OpenTelemetry),
- нет метрик очередей RabbitMQ,
- нет логирования статусов.

В итоге никто не понимает, где именно проблема.

# Итоговый список коррелирует с несколькими ключевыми зонами риска:
## КРИТИЧЕСКИЕ ПРОБЛЕМЫ

1. Долгий расчёт стоимости MES (2–30 минут).
2. Один инстанс MES, CRM, онлайн-магазина.
3. Потеря/задержка сообщений в RabbitMQ.
4. Нет оркестраторов процессов (SAGA) → статусы застревают.
5. MES UI тормозит → операторы не могут брать заказы.
6. БД MES перегружена и не оптимизирована.
7. API открыт без защиты от нагрузки.
8. Нет автоматизированного тестирования → релизы редки и болезненны.

## СРЕДНИЕ

9. Нет idempotency обработки сообщений.
10. Нет DLQ, Retry, Backoff.
11. CRM получает заказы слишком поздно.
12. Тесно связанная архитектура между 3 системами.
13. Нет мониторинга, метрик и логирования.

## ПОТЕНЦИАЛЬНЫЕ

14. У партнёров может начаться формирование негативного Рейтинга API.
15. Команда не успевает обслуживать рост нагрузки.
16. Произойдёт деградация качества всех процессов при росте заказов.

# Инициативы, которые необходимы для устранения нежелательных ситуаций

## A. Архитектура и масштабирование
1. Вынесение расчёта стоимости из MES в отдельный асинхронный Calculation Service.
2. Введение SAGA/Order Orchestrator для управления жизненным циклом заказа.
3. Горизонтальное масштабирование MES (несколько инстансов).
4. Выделение Operator Dashboard API c быстрыми запросами и read-replica БД.
5. Оптимизация запросов MES (индексы, уменьшение payload, CQRS).
6. Переработка партнёрского API в асинхронную модель с JobID + webhooks.
7. Построение RabbitMQ кластера + DLQ, retry, backoff.
8. Введение централизованного лога событий (Event Log / Event Store).
9. Разделение внутренних и внешних очередей; ограничение rate limits.

## B. Надёжность и наблюдаемость
10. Prometheus/Grafana мониторинг RabbitMQ, API, БД, расчётов.
11. Алертинг по времени обработки расчёта, задержкам очередей, отказам.
12. Структурированное логирование + трассировка (OpenTelemetry).

## C. Качество и процессы
14. Автоматизация E2E тестов (Cypress/Playwright).
15. Contract tests и интеграционные тесты с Testcontainers.
16. Реформа CI/CD: автоматический релиз на release + smoke tests.
17. Введение блокирующих quality gates (Sonar, static analysis).

## D. Работа с командой
17. Наём QA automation, ещё одного backend, C#-разработчика и DevOps.
18. Введение регулярного performance-тестирования и chaos-тестов.

# Приоритизация инициатив
## Высокий приоритет (критические, P1)

1. Вынесение расчёта стоимости в Calculation Service
2. RabbitMQ кластер + DLQ/Retry
3. Асинхронный партнёрский API (JobID + Webhooks)
4. Order Orchestrator (SAGA)
5. Оптимизация БД MES (индексы + read-replica)
6. Operator Dashboard API (быстрая выдача новых заказов)

Эти инициативы напрямую устраняют ключевые причины проблем:
— зависания MES,
— потеря заказов,
— задержка статусов,
— жалобы партнёров,
— перегруз UI операторов.

## Средний приоритет (P2)
7. Масштабирование MES.
8. Event Log.
9. Наблюдаемость (Prometheus, Grafana, алерты).
10. Contract tests + Testcontainers.

## Низкий приоритет (P3)

11. CI/CD реформа.
12. Автотесты E2E.
13. Расширение команды.
14. Chaos engineering.

Эти пункты важны, но не гасят пожары «здесь и сейчас».

# Целевая архитектура через 6 месяцев
## Главные принципы архитектуры через полгода:

- асинхронное ядро — никто не ждёт расчётов/обработки;
- горизонтальный масштаб ключевых служб;
- устойчивые очереди;
- чёткая оркестрация статусов;
- наблюдаемость и контроль всех событий;
- быстрые интерфейсы для операторов;
- скорость релизов.

## Высокоуровневая целевая архитектура (через 6 месяцев)
### 1. Calculation Service

- обслуживает расчёты стоимости;
- масштабируется независимо;
- запускается в 3–10 экземплярах;
- минимальная задержка MES.

### 2. RabbitMQ кластер

- отказоустойчивые очереди;
- отдельные очереди для партнёров, CRM, MES.

### 3. Order Orchestrator

- один центр переходов статусов;
- ведёт Event Log;
- восстанавливает зависшие заказы;

### 4. Асинхронный партнёрский API

- POST возвращает jobId;
- webhook + polling;
- rate limits.

### 5. MES

- UI работает от быстрой read-replica;
- сам MES не блокируется тяжёлыми операциями;
- оператор получает новые заказы через WebSocket.

### 6. Наблюдаемость

- метрики расчёта стоимости;
- задержки очередей;
- алерты;
- логирование.

# Три инициативы, которые критично выполнить в течение ближайших 6 месяцев

Если можно выбрать только три — выбираем те, которые устраняют системные причины деградации.

## 1. Вынести расчёт стоимости в Calculation Service (асинхронно)
### Почему:

- это главный bottleneck;
- без него ничего не стабилизируется;
- снижение нагрузки на MES ×10–×50;
- решает ключевую жалобу партнёров и пользователей.

## 2. Ввести асинхронный партнёрский API (jobId + webhook)
### Почему:

- сейчас партнёрский API создаёт лавинообразную нагрузку;
- партнеры — основной двигатель роста;
- без контроля API любые оптимизации рухнут.

## 3. RabbitMQ кластер + DLQ/Retry
### Почему:

- без надёжного брокера все статусы могут теряться;
- CRM и MES не синхронизируются;
- любая другая инициатива бессмысленна, если сообщения пропадают.
