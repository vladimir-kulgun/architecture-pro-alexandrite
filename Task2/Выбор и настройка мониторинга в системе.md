# Мотивация

В текущей архитектуре системы присутствуют признаки быстрых изменений, ручных процессов и неоднородного качества сервисов. Отсутствие централизованного мониторинга приводит к ряду проблем:

## Почему нужен мониторинг

### 1. Отсутствие прозрачности работы системы
Сейчас невозможно быстро определить, где именно произошёл сбой — в API, БД, интеграциях, очередях или на фронтенде.

### 3. Медленное обнаружение инцидентов
Проблемы выявляются по жалобам пользователей или операционным сбоям, а не автоматически.

### 4. Рост нагрузки и бизнес-масштабирование без инструментов контроля
Увеличение количества ювелирных магазинов, заказов и интеграций создаёт риск перегрузки backend-сервисов и баз.

### 5. Неэффективное расследование ошибок
Логи разрознены, нет корреляции между компонентами, что приводит к долгим RCA (root cause analysis).

### 6. Невозможность планировать производительность
Без фактических данных о пиковых нагрузках, медленных запросах и узких местах нельзя корректно планировать рост.

### Что это даст компании

- **Снижение количества инцидентов** и времени простоя.
- **Ускорение разработки** за счёт быстрой диагностики проблем.
- **Прогнозирование нагрузки** и планирование масштабирования.
- **Контроль SLA** для внутренних и внешних сервисов.
- **Повышение качества продукта** за счёт метрик пользовательского опыта.

# Выбор подхода к мониторингу

Для разных частей системы подходят разные модели.
Выбираем подходы:

## API Gateway / Backend API — RED

Почему:
это сетевые сервисы, обрабатывающие запросы. RED идеально подходит.

## PostgreSQL / Redis / очередь сообщений — USE

Почему:
это ресурсы (CPU, RAM, I/O, lock contention, pool usage). USE оптимален.

## Фронтенд / пользовательский опыт — Четыре золотых сигнала

Почему:
критично измерить латентность, ошибки, трафик, насыщенность.

| -------------------------------------------- | -------------- | ------------------------------------- | ---------------------------------------------- | ------------------------------------------------- |

|                                              |                | **Errors (4xx/5xx)**                  | Выявление проблемных эндпоинтов                | `endpoint`, `method`, `status_code`, `error_type` |
|                                              |                | **Duration**                          | Контроль производительности API                | `endpoint`, `method`, `status_code`               |

|                                              |                | **Used memory / fragmentation**       | Предотвращение деградации                      | `redis_instance`                                  |

|                                              |                | **Message age / lag**                 | Выявление медленных consumer'ов                | `queue_name`, `consumer_group`                    |
|                                              |                | **Retries / requeues**                | Обнаружение ошибок обработки                   | `queue_name`                                      |
|                                              |                | **Processing duration**               | Контроль скорости обработки                    | `queue_name`, `consumer_group`                    |
| **Frontend (Web App)**                       | Golden Signals | **Latency (TTFB, LCP)**               | UX и скорость загрузки                         | `page`, `device`, `country`                       |
|                                              |                | **Errors (JS, failed API calls)**     | Качество клиента                               | `page`, `error_type`                              |
|                                              |                | **Traffic**                           | Наблюдение за пользовательской активностью     | `page`, `utm_source`                              |
|                                              |                | **Saturation (WebVitals)**            | Здоровье интерфейса                            | `page`, `metric_name`                             |
| **Интеграции с внешними сервисами**          | RED            | **Call duration**                     | Отслеживание деградации партнёров              | `integration_name`, `endpoint`                    |
|                                              |                | **Error rate**                        | SLA-контроль внешних сервисов                  | `integration_name`, `status_code`                 |
|                                              |                | **Timeout count**                     | Выявление нестабильных интеграций              | `integration_name`                                |
|                                              |                | **Retry count**                       | Анализ устойчивости интеграции                 | `integration_name`                                |
| **Инфраструктура (Node/Pod/Container)**      | USE            | **CPU/RAM usage**                     | Контроль перегрузок                            | `node`, `namespace`, `container`                  |
|                                              |                | **Restarts / OOM kills**              | Обнаружение аварий сервисов                    | `container`, `namespace`                          |
|                                              |                | **Disk usage / Network IO**           | Предотвращение сбоев                           | `node`, `volume`                                  |

# Показатели насыщенности
## Серверы приложений (CRM, MES, Online Store)
| Метрика                      | Порог насыщенности         | Почему важно                               | Действия при превышении                  |
| ---------------------------- | -------------------------- | ------------------------------------------ | ---------------------------------------- |
| **CPU usage**                | > 80% в течение 5 минут    | CPU starvation вызывает задержки API       | Авто-скейлинг + тикет DevOps             |
| **RAM usage**                | > 85%                      | Приложения Java/C# склонны к деградации GC | Увеличение ресурсов / перезапуск / тикет |
| **Thread pool queue length** | > 30 запросов в очереди    | Указывает на нехватку воркеров             | Авто-скейлинг или увеличение пулов       |
| **p95 latency**              | > 1 сек для внутренних API | Задержки ведут к таймаутам у клиентов      | Уведомление backend команды              |

## PostgreSQL
| Метрика                | Порог                           | Почему важно                   | Действия                               |
| ---------------------- | ------------------------------- | ------------------------------ | -------------------------------------- |
| **I/O usage**          | > 70% диска на протяжении 3 мин | Начинаются задержки выборок    | Добавить IOPS / оптимизировать запросы |
| **Active connections** | > 80% от max_connections        | Риск connection storm          | Включить pool, оптимизировать запросы  |
| **Deadlocks**          | > 1 в минуту                    | Признак конкуренции транзакций | Срочный тикет backend                  |

## RabbitMQ
| Метрика         | Порог           | Почему важно                       | Действия                         |
| --------------- | --------------- | ---------------------------------- | -------------------------------- |
| **Queue depth** | > 500 сообщений | Очередь забивается → SLA падает    | Увеличить количество consumer'ов |
| **Message lag** | > 60 сек        | Бизнес-логика начинает запаздывать | Сигнал операторам, auto-scale    |
| **Retry rate**  | > 10%           | Ошибки в обработчиках              | Тикет backend                    |

## Frontend (Web Vitals)
| Метрика                 | Порог              | Почему                             | Действия                           |
| ----------------------- | ------------------ | ---------------------------------- | ---------------------------------- |
| **LCP**                 | > 3.5 сек          | UX деградация → снижение конверсии | Уведомление frontend, CDN-проверка |
| **Error rate (JS)**     | > 1% пользователей | Массовые проблемы клиента          | Тикет FE, rollback версии          |
| **API call error rate** | > 5%               | Бэк сломался                       | Auto-alert backend                 |

## Интеграции
| Метрика          | Порог   | Почему                             | Действия                           |
| ---------------- | ------- | ---------------------------------- | ---------------------------------- |
| **Timeout rate** | > 2%    | Внешний сервис деградирует         | Авто-повтор + уведомление партнёру |
| **Error rate**   | > 5%    | SLA может быть нарушено            | Тикет + fallback логика            |
| **Latency p95**  | > 1 сек | API начинает тормозить всю цепочку | Тикет backend на оптимизацию       |

# Что делать при достижении насыщенности

Вся система реагирует автоматически:

## 🟡 Уровень 1 — Warning

Не критично, но нужно внимание команды.

- Alertmanager шлёт сообщение в Telegram/Slack «DevOps + backend».
- В Grafana появляется предупреждение.
- Создаётся тикет в Jira: auto-created / priority: Medium.

## 🔴 Уровень 2 — Critical

Начинается деградация сервисов.

- Высылается SMS / push / Telegram для on-call инженера.
- Автоматический auto-scaling сервисов (если включён).
- RabbitMQ: увеличивается количество consumer-инстансов.
- DB: включается throttling тяжёлых запросов.
- Auto-rollover на стабильную предыдущую версию (для FE/BE).

## ⚫ Уровень 3 — Emergency

Система близка к падению.

- Звонок on-call инженеру (OpsGenie/PagerDuty/"звонилка").
- Блокировка тяжёлых API операциями.
- Ограничение входящего трафика (rate limit).
- Изоляция проблемных подсистем (circuit breaker).
- Эскалация менеджменту.
