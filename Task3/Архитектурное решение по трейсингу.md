# Мотивация

Внедрение трейсинга критически важно для стабилизации бизнеса в период активного роста.

**Что это даст компании:**

*  **Сквозная видимость:** Возможность отследить путь заказа от нажатия кнопки в **Internet Shop** до появления в **CRM**.


* **Локализация проблем:** Мгновенное понимание, где застрял расчет: в очереди **RabbitMQ** или внутри тяжелого алгоритма в **MES API**.


* **Контроль SLA партнеров:** Доказательная база при жалобах API-пользователей о недошедших заказах.



**Влияние на метрики:**

1. **Lead Time (Бизнес):** Сокращение среднего времени обработки заказа за счет выявления простоев в очереди.
2. **Order Loss Rate (Бизнес):** Снижение процента «потерянных» заказов до нуля.
3. **MTTD / MTTR (Тех):** Сокращение времени обнаружения и устранения инцидентов (Mean Time To Detect / Repair).
4. **Error Rate by Partner (Тех):** Мониторинг качества входящих запросов через API.

---

## Объекты покрытия и данные

* **Internet Shop / API Partner -> MES API:** Точка входа заказа. Здесь он может «отвалиться» по таймауту.


* **MES API -> MES db:** Ожидание блокировок БД при тяжелых расчетах.


* **MES API -> RabbitMQ:** Риск потери сообщения при публикации (Publisher Confirms).


* **RabbitMQ -> CRM API:** Задержки в обработке очереди или ошибки десериализации.



**Данные в трейсе (Span Tags):**

* `order_id` — сквозной идентификатор.


* `customer_id` / `partner_id` — для фильтрации жалоб.


* `polygon_count` — количество полигонов в 3D-модели (влияет на время расчета в MES).


* `calculation_time_ms` — чистое время работы алгоритма в MES.


* `rabbitmq_delivery_tag` — для сверки доставки сообщений.

# Предлагаемое решение

Для реализации мы используем стандарт **OpenTelemetry (OTel)**, так как у нас стек из разных языков (Java, C#, JavaScript).

**Технологический стек:**

* **Collector:** OpenTelemetry Collector для сбора данных.
* **Storage & UI:** **Jaeger** или **Grafana Tempo** для хранения и визуализации трейсов.
* **Интеграция:** Доработка заголовков сообщений в **RabbitMQ** для проброса `trace_id` (Trace Context Propagation).



## Автоматический мониторинг и алертинг

Для предотвращения ситуаций, когда заказ «висит» месяцами, мы внедрим сервис **SLA Monitor**:

1. Он анализирует данные трейсинга в реальном времени.
2. Если для заказа со статусом `SUBMITTED` не появился спан `PRICE_CALCULATED` в течение 40 минут (макс. время 30 мин + запас), система генерирует алерт.


3. Алерты отправляются в Telegram тимлиду и продакт-менеджеру.

# Компромиссы

1. **Стоимость хранения:** Хранить 100% трейсов при росте нагрузки может быть дорого. На начальном этапе будем использовать 100% семплирование, но при кратном росте перейдем на Probabilistic Sampling (например, хранить только 10% успешных и 100% ошибочных трейсов).
2. **Проприетарные модули:** Если библиотека для расчета 3D-моделей в MES закрыта (DLL без исходников), мы сможем обернуть её вызов в спан, но не увидим, что происходит внутри самого алгоритма.


3. **Производительность:** Добавление трейсинга создает небольшой оверхед (1–3% CPU). Учитывая проблемы с производительностью MES db, внедрение агентов трейсинга должно сопровождаться оптимизацией запросов к БД.

# Безопасность

* **Внутренний доступ:** Интерфейс Jaeger будет защищен через **Single Sign-On (SSO)**. Доступ к просмотру трейсов получат только роли «Разработчик», «Тимлид» и «Поддержка».
* **Маскирование данных:** В теги трейсов запрещено записывать PII (персональные данные клиентов, такие как телефон или адрес). Допускаются только технические ID.


* **Сетевой периметр:** Collector будет принимать данные только из внутренней сети облака (Yandex Cloud), внешние API-партнеры не имеют доступа к порту сбора трейсов.
